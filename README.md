# Bismuth

**문서를 그냥 넣으세요. AI 에이전트가 실제로 탐색할 수 있는 폴더 구조가 나옵니다.**

Bismuth는 폴더 하나를 지켜봅니다. 문서가 들어오면 읽고, 정리해 넣고, 그 폴더의 규칙을
적어두고, 원본 옆에 `grep`이 읽을 수 있는 텍스트를 놓습니다. 문서가 들어올 때마다 계속
그렇게 합니다. 처음 몇 문서는 구분할 근거가 생길 때까지 루트에 놓이고, 장서에서 의미 있는
차이가 자라면 그때 폴더가 생깁니다.

사서가 하는 대로입니다 — **맞는 가장 넓은 자리에 넣고, 그 자리가 커지면 쪼갭니다.** 그래서
먼저 들어온 문서가 구조를 결정해버리지 않습니다.

결과물은 진짜 폴더와 진짜 파일입니다. 데이터베이스도, 인덱스도, 내보내기도 아닙니다.
**Bismuth를 지워도 정리된 문서는 그대로 남습니다.**

> 비스무트 결정은 형태 없는 용융물에서 스스로 계단식 격자를 만들며 자랍니다. 같은 발상입니다.

---

## 문제

에이전트 검색은 됩니다. LLM에게 잘 정리된 폴더 트리와 `ls`, `grep`, `read`를 주면
벡터 데이터베이스보다 잘 답합니다. 일 잘하는 신입이 하는 것과 똑같이 하거든요 —
폴더 이름을 읽고, 가설을 세우고, 파일을 엽니다.

문제는 *잘 정리된* 쪽입니다. 같은 에이전트를 50GB의 평평하고 구분 없는 폴더에 붙이면
탐색할 단서가 없습니다. 정확도가 무너집니다.

그래서 누군가 먼저 문서를 정리해야 합니다. 이 프로젝트를 만들게 한 현장에서는
숙련된 두 사람이 **2주**를 썼습니다. 그리고 그 뒤 에이전트의 정확도가 크게 올랐습니다.
구조는 값어치를 했습니다. **2주가 문제였습니다.**

**Bismuth는 그 2주를 없애기 위해, 그리고 문서가 계속 들어와도 계속 없는 상태로 두기
위해 존재합니다.**

## 어떻게 동작하나 — 이게 전부입니다

1. 문서를 넣습니다.
2. Bismuth가 파싱하고, LLM이 읽어 무엇이고 무엇에 관한 문서인지 파악합니다.
3. **이미 있는 폴더들을 보고**, 맞는 기존 폴더 또는 아직 나뉘지 않은 루트에 넣습니다.
4. 문서가 쌓여 구분이 보이면 유지보수 사서가 범주를 제안하고, 안전성 검증을 통과한 계획만
   폴더를 만들고 기존 문서를 옮깁니다.
5. 장서가 더 자라 기존 경계가 틀렸다는 증거가 쌓이면 하위 장서의 모든 표지판과 문서 카드를
   컨텍스트가 제한된 단계로 빠짐없이 다시 보고, 기존 폴더 재사용·병합·이동·폐기를 포함한
   완전한 새 경계를 하나의 원자적 작업으로 적용합니다.

미리 정해둔 카테고리도, 고정된 트리 모양도, 준비 절차도 없습니다. 문서 하나는 분류할 수
없으므로 첫 문서로 폴더를 만들지 않습니다. 분류는 여러 문서 사이의 구분에서 자랍니다.
운영 프롬프트에도 특정 산업·기관·문서 종류의 정답 예시를 넣지 않습니다. 모델은 현재 장서에
실제로 적힌 정보만으로 축을 제안하고, 별도 의미 감사와 파일 안전성 검증을 모두 통과해야
디스크를 바꿀 수 있습니다.

핵심은 **판단에 필요한 현재 경계를 빠짐없이 보여주되 한 컨텍스트에 전부 밀어 넣지 않는 것**입니다. 그래서 계약서를
오늘 `법무/계약` 에 넣고 내일 `계약서/법무` 에 넣어 폴더가 둘로 갈라지는 일 — 이게 이런
도구가 조용히 망가지는 방식입니다 — 을 막습니다. 맞는 기존 폴더가 있으면 새 폴더보다
언제나 우선합니다.

그리고 폴더 구조를 "읽는다"는 것은 **폴더 이름과 한 줄 노트를 보는 것**이지 문서 수천
개를 다시 읽는 게 아닙니다. 그래서 폴더가 200개인 큰 볼트에서도 파일 하나를 배치하는
비용은 일정합니다.

쪼개는 일은 다릅니다. 폴더 하나를 나눌 때는 그 안의 카드를 읽어야 하므로 폴더 크기에
비례하고, 문서마다가 아니라 **폴더가 커졌을 때** 한 번 치릅니다.

### 디스크에 남는 것

```
내지식/
├── _folder.md                      ← 루트 폴더 노트
├── 아폴로/
│   ├── _folder.md                  ← 이 폴더가 무엇을 담는지 한 줄 노트
│   └── 2023/
│       ├── _folder.md
│       ├── 계약서.pdf              ← 당신의 원본. 절대 수정 안 함.
│       └── 계약서.pdf.md           ← 사이드카
├── _inbox/                         ← Bismuth가 추측하기를 거부한 문서
└── .bismuth/                       ← 저널 + 캐시. 지워도 잃을 게 없음.
```

**`_folder.md` — 폴더 노트.** 이 폴더가 무엇을 담는지 적은 한 줄입니다. 두 가지 역할을
합니다. **배치할 때**: 새 문서가 들어오면 Bismuth가 모든 폴더 경로와 노트를 모델에게
보여주고, 모델은 새 폴더를 지어내는 대신 기존 폴더를 재사용합니다 — 노트가 있어야
`법무/계약` 을 다시 쓸지, 빈 경로만 보고 `계약서/법무` 를 새로 만들지가 갈립니다.
**에이전트가 탐색할 때**: 노트는 이 폴더로 들어갈지 말지를 알려주는 힌트입니다.

**`계약서.pdf.md` — 사이드카.** "AI가 쓰기 좋게 재구성"의 실체이고, 그 말보다 훨씬
작습니다: **텍스트가 grep 가능하고, 자기가 뭔지 말합니다.** `grep`은 PDF를 못 읽습니다 —
에이전트가 맞는 파일을 찾아도 열지 못합니다. 그래서 텍스트를 원본 옆에 마크다운으로
놓으면 에이전트의 기존 도구가 그대로 동작합니다. 헤더 블록이 나머지 절반입니다:
*"…계약 기간은 24개월로 한다…"* 같은 grep 결과는 **고아**이고, 고아 조각이 순진한
RAG가 자신 있게 틀리는 이유입니다. 여기서는 그 조각이 **누구의 계약인지 이미 적혀 있는
파일 안에서** 발견됩니다.

**원본은 절대 수정되지 않습니다.** Bismuth는 파일을 옮기고 옆에 새 파일을 쓸 뿐,
당신이 만든 바이트는 건드리지 않습니다.

### 돌아갈 길 없이는 아무 일도 일어나지 않습니다

모든 변경은 파일이 하나라도 움직이기 전에 저널에 기록되고, 모든 작업은 자기를 되돌리는
법을 압니다.

```console
$ bismuth log
a3f2c1  07-17 14:22  bismuth  file 계약서_A기업.pdf -> 아폴로/2023   applied

$ bismuth undo a3f2c1
되돌렸습니다. file 계약서_A기업.pdf -> 아폴로/2023
이 되돌리기 자체가 항목 9b8e0d 이며, 다시 되돌릴 수 있습니다.
```

파일 300개를 옮기다 중간에 죽으면 반쯤 옮겨진 트리에 대한 포렌식이 아니라 **재개 가능한
목록**이 남습니다. 모델의 의견에 따라 당신의 파일을 자동으로 옮기는 프로그램은
이걸 건너뛸 자격이 없습니다.

## 설치와 실행

```console
pip install 'bismuth-kb[parsers,server]'
bismuth
```

끝입니다. 브라우저가 열리고 네 가지를 물어봅니다: 문서를 둘 폴더, 프로바이더, 키,
모델. **Bismuth가 프로바이더에게 당신 키로 실제 쓸 수 있는 모델이 뭔지 물어봅니다** —
찾아볼 모델 이름도, 틀릴 접두사도, 오타 낼 것도 없습니다. 답은
`~/.bismuth/config.json`에 저장됩니다.

작성할 설정 파일은 없습니다. Docker나 CI는 `BISMUTH_*` 환경변수를 쓰면 됩니다 —
[`.env.example`](.env.example) 참고.

그다음 문서를 끌어다 놓으면 됩니다. 처음에는 루트에 놓이고, 서로 구분할 만한 부류가
실제로 모이면 폴더가 생깁니다. 읽을 수 없는 문서만 `_inbox/`에 남습니다.

터미널이 편하다면:

```console
bismuth add 문서.pdf   # 파일을 넣고 정리
bismuth tree           # 결과 보기
bismuth undo <id>      # 어떤 변경이든 되돌리기
bismuth doctor         # 뭐가 설정됐고, 실제로 응답하는지
```

읽는 형식: `.pdf`, `.docx`, `.pptx`, `.xlsx`, `.hwpx`, `.md`, `.txt`, `.csv`.

**한글 문서**는 추가 의존성 없이 기본 지원합니다 (`.hwpx`). AGPL 라이브러리를 쓰지 않고
직접 파서를 만든 이유는 [`docs/licensing.md`](docs/licensing.md)에 있습니다.
구형 바이너리 `.hwp`는 한글에서 `.hwpx`로 다시 저장해 주세요.

## 완전히 로컬로 돌리기

설정 화면에서 로컬 OpenAI 호환 엔드포인트를 사용자 지정 프로바이더로 연결하고 사용할
모델 하나를 고르세요. 그러면 문서와 모델 호출은 외부 프로바이더로 나가지 않습니다. 로컬
게이트웨이에 인증이 필요하면 API 키나 추가 헤더를 함께 설정할 수 있습니다.

Bismuth는 코드 어디에서도 특정 모델 이름을 부르지 않습니다. 모든 작업은 사용자가 설정한
모델 하나를 통하며, 로컬 모델로 바꿔도 코드 경로는 바뀌지 않습니다.

이건 체크박스가 아니라 구조적으로 지탱되는 주장입니다. 문서를 정리할 값어치가 있는
사람이라면 누구나 "문서가 건물 밖으로 나가느냐"를 묻고, 그 답은 포크 없이 *아니오*여야
합니다. 그래서 문서 카드·배치는 스키마와 닫힌 선택으로 제약하고, 구조 유지보수는 Agent Kit이
도구로 장서를 탐색해 완성한 shadow plan을 코드가 검증합니다. 폴더 구조처럼 전체 일관성이
필요한 판단까지 서로 독립적인 분류 호출로 쪼개면 각 호출은 맞아도 도서관 전체가 틀릴 수 있기
때문입니다. 큰 업로드는 최대 50개의 새 카드로 된 bounded 창마다 이 과정을 실행하되, 앞 창이
만든 트리와 폴더 표지판을 다음 창의 공통 기억으로 사용합니다.
[`docs/adr/0004`](docs/adr/0004-llm-provider-abstraction.md),
[`docs/adr/0006`](docs/adr/0006-bismuth-owns-its-configuration.md) 참고.

## 아키텍처

Ports and adapters. 의존성은 안쪽을 향하고, 리뷰어의 성실함이 아니라 **기계적으로**
강제됩니다 (ruff `banned-api`):

```
domain/       값 객체와 순수 함수. I/O 없음, 모델 없음, 파일시스템 없음.
ports/        Protocol. 서비스가 의존해도 되는 유일한 것.
services/     유스케이스. 포트를 알고, 어댑터는 절대 모름.
adapters/     LiteLLM, 파일시스템, 파서, 저널.
container.py  양쪽을 아는 유일한 곳.
```

값어치는 구체적입니다: `container.build()`에 `FakeLLM`을 넘기면 엔진 전체가 — 파싱, 분석,
배치까지 — 네트워크도 키도 비용도 없이 임시 폴더에서 돕니다. 테스트할 값어치가 있는
규칙들(맞는 폴더에 넣는가, 확신이 없을 때 거부하는가, 남의 파일을 안전하게 옮기는가)이
정확히 실제 모델로는 테스트 불가능한 규칙들입니다.

설계 결정과 그 대가는 [`docs/adr/`](docs/adr/)에 기록되어 있습니다. 코드 주석과 문서는
오픈소스 관행에 따라 영어로 쓰여 있습니다. 브랜치·커밋·병합 규칙은
[`docs/git-workflow.md`](docs/git-workflow.md)에 있습니다.

## 상태

알파이고, 그렇다고 말합니다. 배치·사이드카·폴더 노트·삭제·undo 는 실제로 동작하고 테스트됩니다.
모든 로그(LLM 입출력 raw 포함)는 Bismuth를 실행한 위치의 `./logs/`에 쌓이고 재시작마다 초기화됩니다.
아직 안 된 것: OCR, 백그라운드 주기 유지보수, MCP 서버. 큰 업로드는 최대 50건·compact-card
문자 예산으로 나뉘어 창마다 자동 구조 유지보수가 동작하고, 다음 문서는 갱신된 트리를 기준으로
배치됩니다. Agent Kit의 창별 전체 변경안은 가상 검증을 두 번 통과한 뒤 한 저널 트랜잭션으로
적용됩니다. 사용자 승인 단계는 필요하지 않습니다.

**아직 측정하지 않은 것**: 로컬 8B 모델에서의 실제 품질. "로컬이 된다"는 현재 설계에
대한 논증이지 측정이 아닙니다. ADR에도 그렇게 적혀 있습니다.
