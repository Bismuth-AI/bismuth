**문서를 넣으면, LLM 에이전트가 탐색할 수 있는 실제 폴더 구조가 만들어집니다.**

Bismuth는 문서를 읽어 간결한 문서 카드를 만들고, 원본을 일반 파일시스템 트리로
정리합니다. 문서가 쌓이면 기존 폴더를 재사용하고 필요한 가지를 새로 만들며, 더는
맞지 않는 구조를 다시 검토합니다.

결과는 전용 데이터베이스가 아닙니다. Bismuth를 실행하지 않아도 사용할 수 있는 원본
파일, 검색 가능한 Markdown 사이드카, 폴더 노트로 이루어진 디렉터리입니다.

> Bismuth는 완벽한 범용 분류 체계보다 실제로 탐색하기 좋은 구조를 목표로 합니다.

> [!IMPORTANT]
> Bismuth는 알파 단계입니다. 전체 웹 업로드 흐름에서 현재 공식 지원하는 형식은
> PDF, HWP, HWPX, DOC, DOCX, TXT, Markdown이며, 1.0 이전에는 인터페이스가 바뀔 수 있습니다.

## 왜 Bismuth인가요?

도구를 사용하는 LLM은 경로를 확인하고, 폴더를 나열하고, 텍스트를 검색한 뒤 필요한
문서만 열 수 있습니다. 파일시스템 자체가 유용한 탐색 단서를 제공할 때 이 방식이 가장
잘 작동합니다. 평평한 디렉터리에는 그런 단서가 없습니다.

Bismuth는 정리되지 않은 문서 모음을 에이전트가 읽을 수 있는 서고로 바꿉니다.

- 폴더 이름은 탐색 범위를 좁힙니다.
- `_folder.md`는 각 가지에 어떤 문서가 속하는지 설명합니다.
- `<원본>.md`는 추출한 내용과 문서 메타데이터를 `grep`으로 검색할 수 있게 합니다.
- 원본 문서는 계속해서 최종 데이터 원본으로 남습니다.

미리 정해 둔 카테고리 트리나 특정 문서군에 맞춘 few-shot 분류표는 없습니다. 구조는
볼트 안의 문서와 현재 존재하는 트리를 근거로 만들어집니다.

### 무엇이 다른가요?

| | 평평한 폴더 | 기본 벡터 RAG | Bismuth |
| --- | --- | --- | --- |
| 주요 검색 단서 | 파일명과 수동 탐색 | 유사도 순으로 뽑은 텍스트 청크 | 경로, 폴더 범위, 카드, 문서 본문 |
| 원본 문서 정리 | 하지 않음 | 하지 않음 | 저널에 기록하며 실제로 이동 |
| 에이전트 탐색 | 넓은 목록 또는 전체 텍스트 검색 | 한 번의 top-k 결과 | `ls` → `grep` → `read` 반복 탐색 |
| 서비스 없이 사람이 읽기 | 파일은 남지만 구조는 수동 관리 | 원본과 별도로 인덱스 필요 | 일반 폴더와 Markdown 노트만으로 가능 |
| 문서군과 함께 구조 성장 | 수동 | 인덱스만 갱신 | 점진 배치와 구조 정비로 지원 |
| 파일 변경 복구·undo | 파일시스템에 따라 다름 | 원본 배치에는 해당 없음 | 트랜잭션 저널 내장 |

Bismuth는 모든 RAG 시스템을 대체하려는 도구가 아닙니다. 사람과 도구 사용 에이전트가
직접 살펴볼 수 있는 지속 가능한 탐색 구조를 만들며, 필요하면 그 위에 벡터 검색이나
키워드 검색을 함께 사용할 수 있습니다.

## 동작 방식

1. 업로드를 검증하고 안전하게 스테이징합니다.
2. 문서를 파싱하고 내용에 기반한 구조화 카드를 만듭니다.
3. 카드의 제목, 문서 종류, 토픽과 본문 요약을 현재 폴더 트리와 비교합니다. 기존 폴더의
   범위는 제약 조건이지 닫힌 분류표가 아니므로, 목적이 모두 충돌하면 새 최상위 가지를
   만들 수 있습니다.
4. 앞선 결정으로 만들어진 구조를 다음 결정이 사용할 수 있도록 입력 순서대로 배치합니다.
5. 근거가 쌓이면 루트의 느슨한 파일을 묶고, 지나치게 넓어진 가지를 다시 구성하며,
   루트에 남은 파일을 정리합니다.
6. 파일 변경을 저널 트랜잭션으로 적용하고 폴더 노트와 Markdown 사이드카를 갱신합니다.

처리 속도를 위해 문서 준비는 병렬로 수행하지만, 배치는 항상 입력 순서대로 진행합니다.
저장된 카드를 재사용하면 원본을 다시 파싱하지 않고도 폴더 트리를 재구성할 수 있습니다.

## 볼트의 모습

```text
내문서/
├── _folder.md
├── 프로젝트/
│   ├── _folder.md
│   ├── 기획/
│   │   ├── _folder.md
│   │   ├── 로드맵.pdf
│   │   └── 로드맵.pdf.md
│   └── 리서치/
│       └── ...
└── .bismuth/
```

- `_folder.md`: 폴더의 범위를 설명하며 배치와 탐색에 사용됩니다.
- `<원본>.md`: 검색 가능한 추출 텍스트와 문서 카드를 담습니다.
- `.bismuth/`: 저널과 런타임 메타데이터를 저장합니다. 직접 수정하거나 삭제하지 마세요.

Bismuth는 원본 파일 내용을 다시 쓰지 않습니다. 다만 정리 과정에서 원본을 이동하므로
경로는 바뀔 수 있습니다. 생성된 사이드카와 폴더 노트는 Bismuth가 관리합니다.

## 주요 기능

- **문서군 기반 정리** — 미리 정한 카테고리나 도메인 전용 예시 없이 동작합니다.
- **성장하는 폴더 구조** — 문서 모음이 바뀌면 폴더를 재사용하고, 만들고, 묶고,
  기존 가지를 다시 검토합니다.
- **서고 전체 카드 검색** — 파일명, 현재 경로, 제목, 종류, 토픽과 요약으로 문서를 찾고
  결과에서 해당 폴더로 바로 이동합니다.
- **카드 기반 재구성** — 파싱 비용을 다시 쓰지 않고 저장된 카드로 폴더 구조를 비우고
  재구성할 수 있습니다.
- **에이전트 탐색** — 서고 에이전트는 먼저 경로와 폴더 노트를 확인한 뒤 선택한 문서에
  `grep`과 `read`를 사용합니다.
- **되돌릴 수 있는 변경** — 이동, 삭제, 승인된 재구성은 저널에 기록됩니다. 중단된
  트랜잭션은 다음 실행에서 복구하고 완료된 작업은 undo할 수 있습니다.
- **모델 프로바이더 선택** — Anthropic, OpenAI, 그리고 Ollama, LM Studio, vLLM,
  사내 게이트웨이 같은 OpenAI 호환 엔드포인트를 지원합니다.
- **질의 모델 분리** — 문서 정리와 질의응답에 서로 다른 모델 설정을 사용할 수 있습니다.
- **실시간 진행 상황과 진단** — 로컬 웹 UI에서 인제스트 진행 상황, 실행별 모델 호출,
  비용 정보를 확인할 수 있습니다.

## 검색 벤치마크

동일한 한국 법령 문서군, 문항, `qwen3.6-35b` 답변 모델, 정답 전용 채점기를 사용해
Bismuth의 폴더 구조 기반 에이전틱 검색과 튜닝하지 않은 기본 벡터 RAG 기준선을 비교했습니다. 문서군은
300건(4,320쪽, 657만 자), 평가는 88문항입니다. RAG는 1,200자 청크, 200자 겹침,
BGE-M3 임베딩, 코사인 유사도, 한 번의 top-k 검색으로 구성했습니다.

| 지표 | Bismuth 에이전틱 | 기본 RAG top-8 | 기본 RAG top-20 |
| --- | ---: | ---: | ---: |
| 정확도 | **0.98** | 0.78 | 0.81 |
| 만점 문항 | **81 / 88** | 53 / 88 | 52 / 88 |
| 0점 문항 | **0 / 88** | 9 / 88 | 3 / 88 |
| 문항당 LLM 호출 | 16.6회 | **1회** | **1회** |
| 문항당 시간 | 82초 | **8.0초** | 11.5초 |
| 전체 질의 시간 | 41분 | **4.3분** | 6.0분 |

단일 사실 확인 문항에서는 두 방식이 동률이었습니다. 가장 큰 차이는 법령 간 비교
(0.96 대 0.59 / 0.56)에서 나타났고, 버전 구분과 여러 문서를 연결하는 문항에서도 폴더
구조 기반 탐색이 우세했습니다. 88문항 짝지은 비교에서 Bismuth와 RAG top-20의 차이는
+0.164 ± 0.028이었으며 Bismuth가 33문항, RAG가 1문항에서 앞섰습니다.

> [!CAUTION]
> 이 결과는 해당 문서군에서 얻은 근거이지, 에이전틱 검색이 일반적으로 RAG보다 낫다는
> 주장이 아닙니다. Bismuth는 7회의 개발 실행으로 조정한 반면 RAG는 k만 두 값으로 바꾼
> 하나의 의도적으로 기본적인 구성입니다. 리랭커, BM25 하이브리드, 질의 재작성, 조문
> 단위 청킹은 사용하지 않았습니다. 최종 구성별 실행도 한 번뿐이며 답변과 채점에 같은
> 모델이 참여했습니다. 저장소에는 실험 절차와 집계 결과를 공개하지만 벤치마크
> 실행기와 원시 프로바이더 로그는 포함하지 않습니다.

[전체 실험 절차, 카테고리 결과, 근거 도달률 분석과 한계](BENCHMARK.md)를 확인할 수
있습니다.

## 빠른 시작

### 요구 사항

- Python 3.11 이상
- 지원하는 호스팅 모델 API 또는 OpenAI 호환 로컬 엔드포인트

현재 Bismuth는 소스에서 설치합니다.

```console
git clone https://github.com/Bismuth-AI/bismuth.git
cd bismuth
python -m venv .venv
```

가상환경을 활성화합니다.

```bash
# macOS / Linux
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

설치하고 실행합니다.

```console
python -m pip install ".[all]"
bismuth
```

기본 주소는 `http://127.0.0.1:8765`이며 실행하면 브라우저가 자동으로 열립니다. 첫
실행의 설정 화면에서 다음 항목을 입력합니다.

- 문서를 정리할 볼트 폴더
- 모델 프로바이더와 모델
- API 키 또는 OpenAI 호환 엔드포인트 주소

자주 쓰는 실행 옵션:

```console
bismuth --vault ./내문서
bismuth --port 9000
bismuth --no-open
bismuth --help
```

### 5분 튜토리얼

1. **볼트와 모델을 선택합니다.** `bismuth`를 실행하고 로컬 설정 화면을 완료합니다.
   알파 소프트웨어를 평가할 때는 새 폴더나 백업된 폴더를 사용하세요.
2. **대표성 있는 첫 묶음을 올립니다.** 서로 다른 형식과 주제의 문서를 섞어야 첫 가지가
   한 가지 좁은 주제에 치우치지 않고 전체 문서군을 반영합니다.
3. **제안된 서고를 확인합니다.** 트리를 펼쳐 각 폴더의 범위 설명을 읽습니다. 원본은
   생성된 `.md` 사이드카와 나란히 유지됩니다.
4. **찾고 질문합니다.** 이미 아는 문서는 카드 검색으로 찾고, 여러 폴더를 탐색해 근거를
   연결해야 하는 질문은 **서고에 묻기**를 사용합니다.
5. **구조를 키우거나 고칩니다.** 문서를 점진적으로 추가하고, 잘못 놓인 문서는 직접
   옮기고, 저장된 카드로 재배치하거나 저널에 기록된 변경을 undo할 수 있습니다.

빠르게 확인하려면 올바른 분류를 이미 알고 있는 TXT나 Markdown 파일 몇 개로 시작하세요.
큰 문서군이나 민감한 자료를 넣기 전에 경로와 폴더 설명이 기대와 맞는지 확인하는 것이
좋습니다.

설정은 `~/.bismuth/config.json`에 저장됩니다. 환경변수 기반 설정이 필요하면
문서화된 `BISMUTH_*` 변수가 들어 있는 [`.env.example`](.env.example)을 `.env`로
복사하세요.

## 모델 백엔드

설정 화면에서 다음 백엔드를 선택할 수 있습니다.

- Anthropic
- OpenAI
- Ollama, LM Studio, vLLM, 사내 게이트웨이를 포함한 OpenAI 호환 서버

로컬 엔드포인트의 기본 예시는 `http://localhost:11434/v1`입니다. 정리 품질은 모델의
지시 이행 능력, 구조화 출력 안정성, 컨텍스트 크기에 영향을 받습니다. 소형 로컬 모델의
품질은 아직 체계적으로 측정하지 않았습니다.

문서 텍스트는 사용자가 설정한 모델 엔드포인트로 전송됩니다. 개인정보 요구사항에 맞는
엔드포인트를 선택하고 운영하세요.

프로바이더 인증 정보는 운영체제 키체인이 아니라 로컬 `~/.bismuth/config.json`에
저장됩니다. 플랫폼에서 지원하는 경우 이 파일은 현재 사용자만 읽을 수 있는 권한으로
생성됩니다.

### 모델 공개와 독립 구동

Bismuth는 모델 가중치를 포함하거나 모델을 추가 학습하지 않습니다. 사용자가 선택한 기존
모델을 변경 없이 사용합니다. 전체 파이프라인 검증에 사용한 오픈웨이트 기준 모델은
Apache-2.0으로 공개된
[`Qwen/Qwen3.8-27B-FP8`](https://huggingface.co/Qwen/Qwen3.8-27B-FP8)입니다.
Anthropic과 OpenAI는 선택 가능한 호스팅 프로바이더이며 필수 실행 조건이 아닙니다.

독립적으로 구동하려면 vLLM과 같은 OpenAI 호환 서버로 기준 모델을 실행할 수 있습니다.

```console
vllm serve Qwen/Qwen3.8-27B-FP8 --port 8000
```

Bismuth 설정에서 **OpenAI 호환 서버**를 선택하고 엔드포인트에
`http://127.0.0.1:8000/v1`, 모델에 `Qwen/Qwen3.8-27B-FP8`을 입력합니다. 모델은 의미
판단을 제안하지만, 문서 파싱, 스키마·경로 검증, 저널 기반 파일 트랜잭션, 복구와 undo는
Bismuth의 공개 소스코드가 수행합니다. 따라서 호스팅 모델의 응답을 단순 전달해야만
작동하는 구조가 아닙니다.

모델·라이브러리·프레임워크·개발 도구의 출처와 라이선스는
[`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)에 공개합니다. CI는 각 커밋에서 실제로
해결된 전이 의존성 전체의 라이선스 목록도 아티팩트로 게시합니다.

## 현재 지원 범위

전체 제품 흐름에서 지원하는 기능:

- PDF, HWP, HWPX, DOC, DOCX, TXT, Markdown 업로드와 텍스트 추출
- 요청당 최대 500개, 파일당 50MB, 전체 500MB
- 문서 카드, Markdown 사이드카, 폴더 노트
- 점진적 정리와 카드 기반 전체 재배치
- 저널 기반 undo를 지원하는 수동 이동과 삭제
- 폴더 구조를 활용하는 질의응답
- 실행별 LLM 진단과 사용량 집계

현재 지원하지 않는 기능:

- 스캔 PDF용 OCR
- 외부 네트워크에 공개하는 인증 서버
- 백그라운드 주기 정리
- MCP 서버
- 소형 로컬 모델의 정리 품질 보장

다른 형식의 파서 어댑터도 코드에 포함되어 있지만, 해당 형식은 아직 전체 업로드·분석
흐름의 공식 지원 대상이 아닙니다.

## 아키텍처

Bismuth는 ports and adapters 구조를 사용하며 Ruff 규칙으로 의존성 방향을 검사합니다.

```text
domain/       값 객체와 순수 규칙
ports/        애플리케이션이 요구하는 Protocol
services/     인제스트, 배치, 구조 정비, 탐색, 트랜잭션
adapters/     LLM, 파일시스템, 파서, 카탈로그, 저널 구현
prompts/      구조화된 문서군 중립 모델 지시문
agentkit/     내부 프로바이더 중립 도구 호출 에이전트 루프
api/          FastAPI 애플리케이션과 로컬 웹 UI
cli/          로컬 웹 애플리케이션 실행 진입점
container.py  의존성 조립 지점
```

테스트에서는 스크립트형 모델과 임시 볼트를 주입하므로 API 키 없이도 핵심 정리, 복구,
API 동작을 검증할 수 있습니다.

## 데이터 안전과 진단 기록

모든 파일시스템 변경은 적용 전에 저널에 기록됩니다. 트랜잭션 도중 프로세스가 중단되면
Bismuth가 완료되지 않은 기록을 감지하고 다음 실행에서 롤백합니다.

진단 기록은 `./logs/`에 저장됩니다. `./logs/runs/<run_id>/` 아래의 실행별 기록은
자동으로 삭제되지 않습니다. 여기에는 추출한 문서 텍스트, 프롬프트, 모델 입력과 출력이
포함될 수 있습니다. 버그 리포트에 첨부하기 전에 내용을 검토하고 민감정보를 제거하세요.
로그 폴더는 Git에서 무시됩니다.

웹 애플리케이션에는 인증이 없으며 의도적으로 루프백 주소에만 바인딩됩니다. 외부
네트워크에 직접 노출하지 마세요.
