# 랄프 루프 운영

> **루프마다 [CHECKLIST.md](CHECKLIST.md)를 먼저 읽는다.** 이 문서는 절차의 근거이고,
> 그쪽이 한 화면짜리 실행 목록이다. 산문으로 적힌 절차는 읽히지 않는다 — 아래 항목은
> 전부 여기 쓰여 있었는데도 빠뜨린 것들이다.

한 라운드 = 새 볼트에 문서 N건을 넣고, 결과를 보고, **원인을 로그에서 확인하고**, 고치고,
다시 돌리는 것.

가운데 항목이 빠지면 루프는 아무 의미가 없다. 실제로 열여덟 라운드를 개수만 보고 돌린 적이
있고, 그때 놓친 결함들이 호출 기록 **하나**를 열자 바로 나왔다([사례](#사례-호출-하나에서-나온-결함-넷)).
숫자는 어디가 아픈지 알려주지만 **왜 아픈지는 증명하지 않는다**([SPEC 6.3](../../SPEC.md)).

---

## 1. 돌리기

```bash
python scripts/ralph.py <이름> --docs 30
```

| 옵션 | 뜻 |
|---|---|
| `--docs N` | 문서 수. 코퍼스 전체에 고르게 퍼뜨려 고른다(앞에서 N개가 아니다) |
| `--ahead N` | 배치보다 앞서 읽고 카드를 만드는 문서 수 (기본 8, `1`이면 순차) |
| `--concurrency N` | 동시 모델 호출 (기본 12). 20에서 문서가 유실된 적이 있다 |
| `--reverse` | 같은 선택을 역순으로. 순서 독립성 확인용([SPEC 3.5](../../SPEC.md)) |
| `--seed N` | 고르게 퍼뜨리는 대신 무작위 표본 |

볼트는 `~/bismuth-runs/<이름>`, 로그는 `~/bismuth-runs/<이름>-logs`에 생긴다. 로그가 볼트
안에 있으면 모델 눈에는 그냥 형제 폴더라서 밖에 둔다.

### 규모는 올려가며

구조가 안정되기 전에 300건부터 돌리면 한 번에 74분을 쓰고 배우는 건 별로 없다.

| 문서 | 대략 | 쓰는 곳 | 올라가는 조건 |
|---|---|---|---|
| 30건 | 3분 | 수정 하나가 의도대로 동작하는지. 트리를 통째로 읽을 수 있다 | **3회 연속** 회귀 없음 |
| 100건 | 7분 | 결함이 사라졌는지, 새 결함이 생겼는지 | **3회 연속** 실격 없음 |
| 300건 | 20분 | 기준선 대조 | — |

**한 단계에서 3회를 채우기 전에는 올라가지 않는다.** 재실행 편차가 기준 폭보다 크므로
한 라운드가 좋아 보이는 것은 신호가 아니다. 실제로 100건을 세 번 돌리고 그중 한 번이
좋았을 때 300건으로 올라간 적이 있고, 그 뒤 300건을 서른다섯 번 돌리는 동안 100건은
세 번에 머물렀다 — 제일 비싼 자리에서 제일 오래 두들긴 셈이다.

싼 자리에서 잡히는 결함이 비싼 자리에서도 같은 결함이다. 30건에서 트리 전체를 읽을 수
있다는 것이 그 단계의 진짜 이점이고, 300건에서는 그게 안 된다.

### 한 번으로는 아무것도 판정 못 한다

**같은 코드·같은 문서·같은 순서로 두 번 돌리면 다른 트리가 나온다.** `temperature=0.0`이고
애플리케이션이 표본추출을 소유하는데도 그렇다 — 추론 서버가 요청을 배치로 묶으면 수치가 달라진다.

그래서 수정 하나를 라운드 하나로 판정하면 노이즈를 신호로 읽는다. 실제로 같은 코드의 두 실행
차이를 "순서 의존성"으로 오진한 적이 있다(루트 폭 22 대 9). 결함이 **여러 라운드에 걸쳐**
사라졌는지를 봐야 한다.

## 2. 루프가 끝나면

순서대로 한다. 앞 단계가 뒷 단계의 대상을 정한다.

### 2.1 셀 수 있는 것 — 어디가 아픈지

```bash
python scripts/measure_vault.py ~/bismuth-runs/<이름>
```

실격선(폭 20·깊이 5·잎 50) → 형태 불변식(통과 폴더, 미분해 더미) → 권장 띠 순으로 나온다.
**여기서 순위를 매기지 않는다.** 이건 어느 가지를 열어볼지 고르는 도구다.

### 2.2 트리를 읽는다 — 무엇이 아픈지

```bash
python - <<'PY'
import os
for dp, dn, fns in os.walk(os.path.expanduser("~/bismuth-runs/<이름>")):
    dn[:] = sorted(d for d in dn if d != "_inbox" and not d.startswith("."))
    if ".bismuth" in dp:
        continue
    docs = sorted(f for f in fns if f.lower().endswith(".pdf"))
    note = os.path.join(dp, "_folder.md")
    purpose = ""
    if os.path.exists(note):
        body = open(note, encoding="utf-8").read().split("---", 2)[-1]
        lines = [l.strip() for l in body.splitlines() if l.strip() and not l.startswith(("#", ">"))]
        purpose = lines[-1] if lines else ""
    d = dp.count(os.sep)
    print("  " * d + f"[{os.path.basename(dp) or '(루트)'}] {len(docs)}건  ↳ {purpose[:70]}")
    for f in docs[:6]:
        print("  " * d + "    · " + f.split("(")[0][:56])
PY
```

[docs/eval/README.md](../eval/README.md)의 채점표대로 결함을 센다. 폴더 이름과 그 안의
문서를 **직접 대조한다** — 이름이 안의 문서를 가리키는가, 형제가 서로 배타적인가, 노트만 읽고
열지 말지 정할 수 있는가.

기록은 `docs/eval/<라운드>.md`에.

### 2.3 결함마다 그걸 만든 호출을 연다 — 왜 아픈지

**이 단계를 건너뛰면 루프를 돌린 의미가 없다.**

결함이 있는 폴더 경로로 그 폴더를 건드린 모든 것을 뽑는다:

```bash
python scripts/inspect_run.py ~/bismuth-runs/<이름>-logs --folder "산업지원/금융규제"
```

`# --call llm_…` 줄이 같이 나온다. 그 호출을 연다:

```bash
python scripts/inspect_run.py ~/bismuth-runs/<이름>-logs --call llm_4c17afcc5de640afbd1ca0575ef187ad
```

나오는 것: `system`/`user` 전문, 스키마, 모델과 생성 설정, 그 요청에서만 유효했던 핸들,
그리고 응답의 `raw` · `reasoning_content` · `finish_reason` · 시도별 `ms`.

다른 진입점:

```bash
--document <document_id>   문서 하나의 전 생애 (배치 → 카드 → 이동)
--stage subdivision.review 단계 하나의 모든 호출
--event subdivide.rejected 거부된 것만
--window sketch:docs-002   패킷 하나
```

인자 없이 부르면 매니페스트와 이벤트·단계 집계가 나온다. 큰 것부터 보고 좁혀 들어간다.

### 2.4 코드를 고친다

관측한 실패 단계와 바꿀 코드 경계를 **일대일로** 잇는다. 커밋 메시지에 무엇을 관측했는지
숫자와 함께 적는다. 그래야 나중에 그 수정이 근거 있는 것이었는지 되짚을 수 있다.

Fake LLM 테스트와 정적 검사는 계약과 안전성을 지키지만, **실제 분류 품질이 나아졌다는 근거는
되지 못한다**(SPEC 6.3).

## 3. 시간이 어디로 가는지

```bash
python scripts/where_the_time_went.py ~/bismuth-runs/<이름>-logs
```

단계별 시작·종료와 호출별 elapsed로 계산한다. 로그 줄 간격이나 총 토큰으로 추정하지 않는다.

300건 한 라운드의 실측 분포(호출 9,928회, 76분):

| 단계 | 비중 | 성격 |
|---|---|---|
| 카드 생성 | 57% | 문서에만 의존 → `--ahead`로 병렬 |
| 멤버십·라우팅 | 30% | 문서당 닫힌 질문. 이미 병렬 |
| 나머지 | 13% | 배치는 그중 1.9%뿐 |

## 4. 하지 말 것

- **숫자만 보고 코드 고치기.** 개수는 가설이지 원인이 아니다
- **한 라운드로 판정하기.** 재실행 편차가 기준 폭보다 크다
- **트리 안 읽고 넘어가기.** `A/B/C`로 나눠도 숫자는 만점이 나온다
- **구조 안 잡혔는데 300건 돌리기.** 74분 쓰고 배우는 게 30건과 같다
- **테스트 통과를 품질 근거로 쓰기.** Fake LLM은 계약을 지킬 뿐이다

## 사례: 호출 하나에서 나온 결함 넷

r19에서 `금융산업 구조개선` 폴더가 51건을 담았는데 그중 4건만 그 주제였다. 나머지는
중대재해처벌법, 과학기술기본법, 국립공업고등학교 설치령이었다.

개수만 보면 "잎이 크다"까지다. `subdivide.replaced` 이벤트까지 보면 "재작성이 범인"까지다.
**호출을 열자** 네 가지가 한꺼번에 나왔다:

```
--call llm_4c17afcc…   stage=subdivision.replacement  window=sketch:reduce-002-001
```

1. `basis` 필드에 영어 추론 문단 400자가 들어와 있었다. `is_axis_label`은 빈 값·개행만 막는다
2. 축약이 통합이 아니라 **선택**이었다 — 서로 다른 축의 두 후보를 못 합치고 하나를 버렸다.
   102건의 경계를 36건짜리 패킷이 정했다
3. 표지 여섯 개가 전부 `sign == name`이었다. 그게 `<축>: <이름>` 노트의 직접 원인이다
4. 한국어 코퍼스인데 한 패킷의 응답이 영어였다 — 이 경로에 언어 앵커가 없다

셋은 로그 집계로는 보이지 않고, 넷째는 아예 이벤트가 없다.
